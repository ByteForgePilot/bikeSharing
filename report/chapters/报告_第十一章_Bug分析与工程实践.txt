================================================================
    共享单车多传感器数据采集与健康检测系统

    第十一章  Bug 分析与工程实践
================================================================



11.1  引言
================================================================

软件开发过程中的 Bug 往往比正常流程揭示更多关于系统设计的深层信息。
本章记录本项目从 v1.0 到当前版本中遇到的七个关键 Bug，分析其根因、
影响范围和修复策略，并从中提炼出对后续类似项目的工程实践建议。



11.2  Bug 1：F1 P 值异常偏高（v1.0 → v2.0）
================================================================

  **现象**：F1 轮胎偏摆检测的 P 值高达 177，远超预期范围（正常
  约 0.1~1.0）。导致所有车辆的 F1 评分均为 0，检测器完全失效。

  **根因**：FFT 幅值未做归一化。NumPy 的 fft() 函数返回未经缩放的
  复数结果，其模值正比于信号长度 N。原始代码直接用 mag[idx] 作
  为幅值，对于 N=6000 的输入信号，幅值被放大了约 3000 倍。

  **修复**：FFT 幅值除以 N/2（正弦波在 FFT 中的理论归一化系数）。

      # 修复前
      mag = np.abs(fft(az))[:n//2]

      # 修复后
      mag = np.abs(fft(az))[:n//2] / (n/2)

  **教训**：FFT 的幅值归一化是信号处理中最容易犯的低级错误之一。
  在算法验证阶段应首先用已知频率的正弦波测试信号验证 FFT 流程的
  端到端正确性，而非直接在真实骑行数据上调试。



11.3  Bug 2：F2 异常分恒为 1（v1.0 → v2.0）
================================================================

  **现象**：所有输入音频的 F2 异常得分（anomaly_score）恒为 1.0，
  导致评分始终为 0。

  **根因**：v1.0 的 F2 使用单一特征（高频能量比）判定异常，该特
  征在共享单车骑行音频中的值几乎恒定高于阈值（2~4kHz 频带的能量
  本身就较高，无论是否异响）。单特征+单阈值的方案无法建立有效的
  决策边界。

  **修复**：从单特征切换为四维加权融合（高频能量比 + MFCC 高低频
  比 + 峰值因子 + 冲击率），每维分别归一化后加权求和。虽然 v1.0
  的 MFCC 方案后来在 v3.0 中被包络谱替代，但"多特征融合优于
  单特征阈值"这一原则贯穿始终。

  **教训**：单特征决策的本质问题是对噪声维度的信息丢失——任何单一
  特征在复杂声学环境下都有盲区。多特征融合即使权重未经优化，其
  鲁棒性也远优于精细调参的单特征方案。



11.4  Bug 3：F3 零个直行段（v1.0 → v2.0）
================================================================

  **现象**：F3 车头不正检测的 straight_segments 始终为 0，所有输入
  返回满分（数据不足以判断）。

  **根因**：v1.0 使用绝对阈值（gz 方差 < 某个固定值）判定直行段。
  但在起伏路面或非职业骑手的骑行中，几乎没有一个 5 秒窗口的 gz
  方差低于该阈值——直行段的定义为"接近于零"，而实际骑行数据
  中即使是直线骑行的 gz 方差也有约 0.05~0.15 rad/s 的波动。

  **修复**：放弃绝对阈值，改用相对排名——取 gz 方差最低的 30%
  窗口作为准直行段。同时加入绝对质量门（最低方差仍不得超过
  0.3 rad/s），防止"全是弯道的蛇形骑行"被误判有直行段。

  **教训**：在传感器数据质量不可控的户外场景中，相对阈值（排序/
  百分位）比绝对阈值更鲁棒。绝对阈值的标定依赖特定设备、特定
  环境和特定用户的组合，换一个城市/手机/骑手就可能失效。



11.5  Bug 4：中文终端编码乱码（Windows）
================================================================

  **现象**：Python 算法在 Windows 终端运行时所有 print 输出的中文
  字符显示为乱码（如"浼犳劅鍣?鏁版嵁"）。

  **根因**：Windows 的默认控制台编码为 GBK（代码页 936），而 Python
  源代码为 UTF-8。sys.stdout 的编码在 Windows 上自动设为 GBK，
  与源文件编码冲突。

  **修复**：在 main() 函数开头强制设置 UTF-8：

      if sys.platform == "win32":
          try:
              sys.stdout.reconfigure(encoding="utf-8")
          except Exception:
              pass

  同时在所有文件打开操作中显式指定 encoding="utf-8"。

  **教训**：跨平台开发中，编码问题是最容易被忽视但影响面最广的
  非功能性 Bug。建议在 CI 中加入 Windows 构建节点，将终端编码
  作为常规测试项。



11.6  Bug 5：Android 暂停失效（v1.1 → v1.2）
================================================================

  **现象**：用户点击「暂停采集」按钮后，前台服务通知消失但传感器
  回调仍在继续——加速度计和陀螺仪数据继续写入文件，音频持续录制。

  **根因**：pauseCollection() 中调用了 collectionJob?.cancel()，
  但 cancel() 仅向协程发送取消信号，不会强制中断。各采集协程内部
  使用 delay(Long.MAX_VALUE) 挂起等待——cancel() 确实触发了
  CancellationException，但在 cleanupSession() 的 finally 块中
  调用 withContext(NonCancellable + Dispatchers.Main) 执行清理。
  问题在于 Android 传感器注销（unregisterListener）必须在主线程
  调用，而协程取消后的 withContext(NonCancellable) 中的某些操作
  可能被调度到非主线程，导致 unregisterListener 未被实际执行。

  **修复**：在 cleanupSession() 中显式使用 withContext(Dispatchers
  .Main) 包裹每个 Collector 的 stop() 调用，确保传感器注销在主线程
  上执行。

  **教训**：Kotlin 协程的取消是协作式的（cooperative），不能简单
  等同于"杀死线程"。涉及原生 API（如 SensorManager、AudioRecord）
  的资源释放时，必须显式确认 stop() 在正确的线程上执行，而非依赖
  协程的自动清理。



11.7  Bug 6：综合评分对低分过度惩罚（v3.0 参数调优）
================================================================

  **现象**：在真实骑行数据的初期测试中，一辆 F1=71/F2=92/F3=94
  的单车综合评分仅 56 分（建议换车），而该车实际仅有轮胎轻微偏摆，
  远未到需要更换的地步。另一辆 F1=80/F2=95/F3=82 的单车综合评分
  84 分（推荐骑行），与其"轮胎有待观察"的保守判断也不完全吻合。

  **根因**：v3.0 的 penalty = (min/100)^0.6 在低分值段的衰减过于
  激进。当 min=71.2 时，penalty=0.712^0.6=0.815，配合调和平均后
  综合分仅为 56，严重偏离了"71 分轮胎不致命"的实际判断。

  **调优过程**：
    ① 尝试 penalty = (min/100)^1.0（线性）：min=71→penalty=0.71，
       综合分约 53，更糟。
    ② 尝试 S = H（纯调和平均，不加 penalty）：(6)=84，(2)=83，
       用户反馈"太高了，两个都不推荐"。
    ③ 折中：penalty = (min/100)^0.7。该指数在 min=71 时 penalty
       =0.79，综合分分别为 72（谨慎）和 65（谨慎），形成合理的
       梯度区分。

  **最终公式**：S = H × (min/100)^0.7

  **教训**：幂指数 0.1 的微调即可显著改变评分分布的倾斜程度。
  在处理"保守 vs 激进"这类主观偏好问题时，参数化（而非硬编码）
  是唯一正确的工程策略——将幂指数设为常量而非魔数，允许部署方
  根据自身风险偏好调整。



11.8  Bug 7：F2 对正常车评分偏低（v3.0 参数调优）
================================================================

  **现象**：两辆链条状态已知良好的单车，F2 评分分别为 84.8 和
  87.7。用户反馈："两个车都没有异响问题，评分应该有 90"。

  **根因**：F2 的异常得分分段评分中，满分区间为 anomaly < 0.20，
  而正常骑行固有的踏频调制（正常的踏板运动）将 anomaly 推至
  约 0.30~0.33 区间——刚好进入 0.20~0.45 的下滑区。

  **调优过程**：
    ① 将满分区间从 <0.20 放宽到 <0.30：(6)→99.7, (2)→96.1。
       用户反馈"太高了"。
    ② 回缩至 <0.25，同时降低下滑斜率（30→25）：(6)→94.8,
       (2)→92.4。用户确认合理。

  **最终参数**：

      anomaly < 0.25       → 100
      0.25 ≤ anomaly < 0.50 → 100 - 25*(anomaly-0.25)/0.25
      0.50 ≤ anomaly < 0.70 → 70 - 40*(anomaly-0.50)/0.20
      anomaly ≥ 0.70       → max(0, 30 - 30*(anomaly-0.70)/0.30)

  **教训**：算法开发中的参数调优不应属于纯粹"算法工程师的工作"，
  也应纳入实际使用者的直觉反馈。0.25 vs 0.30 的区别在训练数据
  上可能无统计显著差异，但对用户感知的评分合理性影响巨大。



11.9  工程实践总结
================================================================

从上述七个 Bug 的根因和修复中，提炼以下工程实践准则：

  (1) 信号处理流程的单元测试不可省略。

     Bug 1（FFT 未归一化）和 Bug 2（单特征失效）都可以在合成测试
     信号上暴露。用已知频率/幅值的正弦波测试 FFT 管线，用已知周期
     冲击模式的合成音频测试包络谱+Cepstrum 管线——这些测试的成本
     远低于在真实骑行数据上盲调。

  (2) 户外场景的传感器数据不可靠，算法必须防御。

     Bug 3（F3 零直行段）和 Bug 5（Android 暂停失效）的根因都与
     实际环境偏离理想假设有关。算法中的绝对阈值应尽可能替换为
     相对排名或自适应门限；涉及原生 API 的操作应显式指定线程
     而非依赖框架默认行为。

  (3) 关键参数必须显式化、可配置。

     Bug 6（penalty 幂指数）和 Bug 7（F2 满分区间）的调优过程中，
     每次改动只需修改一个常量即可重跑全部验证。若这些值散落在
     函数内部的数值字面量中（如 "0.6" 直接出现在公式而非常量
     定义中），调优将变成一场代码搜索和批量替换的噩梦。

  (4) 用户直觉是参数标定的重要输入。

     算法工程师的"最优"（在测试集上均方误差最小）可能并非使用者
     的"合理"（评分梯度与直觉一致）。Bug 6 和 Bug 7 的调优本质上
     是在数值最优解和用户期望之间寻找平衡——前者来自数据分布，
     后者来自业务上下文，两者不可互相替代。

  (5) 跨平台开发必须纳入 CI。

     Bug 4（Windows 中文乱码）如果有一台 Windows CI 节点就会在
     首次提交时暴露。本项目当前在 GitHub Actions 中仅有 backend-test
     和 mobile-build 两个 workflow，应补充 Windows 平台的编码验证步骤。



11.10  本章小结
================================================================

七个 Bug 覆盖了信号处理基础错误（Bug 1）、特征工程缺陷（Bug 2）、
阈值设计失误（Bug 3）、跨平台编码（Bug 4）、Android 生命周期（Bug 5）、
评分公式调优（Bug 6）和参数标定（Bug 7）七个不同维度。其共同指向
一个工程原则：**在不可控的物理世界中部署算法系统，防御性设计、
参数显式化和用户反馈闭环比模型精度更重要。**
