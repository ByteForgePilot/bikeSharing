================================================================
    共享单车多传感器数据采集与健康检测系统

    第二章  系统总体设计
================================================================


2.1  系统设计目标与约束
================================================================

在展开具体设计之前，有必要明确本系统面临的设计目标与硬性约束条件。
这些约束直接塑造了后续各层的架构决策。

2.1.1  设计目标

  (G1) 低成本部署：巡检人员使用现有安卓手机即可完成全部数据采集，
        无需采购专用嵌入式硬件（如ESP32、工业传感器模块）。手机端
        仅需安装一个APK，无额外配件。

  (G2) 零训练数据依赖：算法完全不依赖机器学习标注数据集。所有故障
        判定基于经典信号处理的物理先验知识。这一点对于快速推广至
        不同城市、不同车型、不同工况具有重要意义——无需在每个部署
        场景重新标注训练数据。

  (G3) 量化输出：健康评估结果必须是0~100连续数值，而非简单的
        "好/坏"二分类。量化评分允许运维系统按需求灵活设置调度阈值，
        实现精细化车队管理。

  (G4) 可解释性：每个检测器的评分过程必须透明可解释。运维人员应当
        能够理解"为什么这辆车的轮胎偏摆评分为45分"——是轮频处振动
        幅值过高？还是平整路面占比太低导致置信度下降？而非面对一个
        黑盒机器学习模型的结论无从考证。

  (G5) 松耦合架构：采集端、算法端、可视化端三者独立可替换。例如，
        如果未来改用ESP32嵌入式方案替代手机采集，算法端不应受到
        任何影响——只要输入文件遵循既定的数据格式规范即可。

2.1.2  硬性约束

  (C1) 传感器带宽受限：手机MEMS加速度计标称带宽约100Hz（可利用的
        线性范围约40Hz以下），陀螺仪约50Hz。这与工业振动分析中常用
        的压电式加速度计（带宽10kHz以上）存在两个数量级的差距。算法
        必须在低频区提取足够的故障信息。

  (C2) 音频采样率受限：Android AudioRecord API在省电模式下通常采用
        8kHz采样率。根据奈奎斯特定理，可分析频率上限为4kHz。链条金属
        冲击的共振频带恰好落在2~4kHz范围内，采样率恰好够用，但没有
        余量。更高的采样率会显著增加文件大小和处理时间。

  (C3) GPS可用性不保证：城市峡谷（高楼间）、隧道、高架桥下等场景中
        GPS信号频繁中断。算法必须具备在无GPS条件下的独立工作能力。

  (C4) 计算资源受限：算法在巡检人员的笔记本电脑上离线运行，不应
        依赖GPU或云计算资源。单次分析时间需控制在30秒以内，以保证
        现场巡检的工作流不被中断。

  (C5) 存储空间有限：一次典型骑行采集（15分钟）的传感器数据约
        50~200 MB（取决于GPS和音频数据量）。巡检人员一天可能采集
        数十辆单车的数据，总存储需求在GB级别。手机端需使用合理的
        存储策略（公共Documents目录或应用私有目录回退）。



2.2  系统总体架构
================================================================

2.2.1  三层架构设计

本系统采用经典的三层架构（Three-Tier Architecture），自下而上分为
采集层、算法层和可视化层。层与层之间通过标准化的文件格式解耦。

  ┌─────────────────────────────────────────────────────────────┐

  │                                                             │
  │   Flask Web Server  ←→  ECharts 仪表盘                       │
  │   /api/process 接口接收文件上传，返回JSON图表数据              │
  │   健康评分仪表盘  |  三维雷达图  |  信号波形/频谱面板           │
  └────────────────────────┬────────────────────────────────────┘
                           │  文件上传 (multipart/form-data)
                           │  或直接读取本地文件
  ┌────────────────────────▼────────────────────────────────────┐
  │                    算法层 (Business Logic)                    │
  │                                                             │
  │  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
  │  │ 数据预处理     │  │ 三级检测管线  │  │ 综合评分引擎  │       │
  │  │              │  │              │  │              │       │
  │  │• 格式解析     │  │ F1 轮胎偏摆   │  │ 加权调和平均  │       │
  │  │• 时间对齐     │  │ F2 链条异响   │  │ 最小值惩罚    │       │

  │  输入: 传感器数据.txt + 音频.pcm + 音频_时间戳.csv             │

  │                   音频_时间戳.csv                              │
  └─────────────────────────────────────────────────────────────┘

图2-1  系统三层架构图

每一层的核心职责和边界如下：

  采集层：只负责"记录"。不进行任何信号分析或特征提取。最大化数据
  保真度——以传感器的原生采样率写入文件，不做降采样或压缩。输出为
  三个标准格式文件。

  算法层：只负责"分析"。从文件系统读取原始数据，完成全部预处理和
  故障检测计算，输出结构化的JSON结果。算法层不关心数据是如何采集
  的——只要文件格式符合规范即可。

  可视化层：只负责"展示"。接收算法层的JSON输出（通过文件或HTTP），
  渲染为交互式图表。可视化层不包含任何分析逻辑。

2.2.2  数据流向

一次完整的系统使用流程涉及以下数据流动步骤：

  Step 1 — 骑行采集：巡检人员携带安装本App的安卓手机，扫码开锁后
         点击「开始采集」。手机进入前台服务模式，四类传感器同步
         开始记录。骑行过程中屏幕可关闭，采集不中断。

  Step 2 — 保存归档：骑行结束点击「暂停采集」。数据被写入手机存储
         的 Documents/自行车数据/20250610_143025/ 文件夹内。巡检人员
         通过USB或云盘将文件夹传输至笔记本电脑。

  Step 3 — 离线分析：在笔记本电脑上运行 bike_health_detector.py，
         读取传感器数据和音频文件，执行三级检测。终端输出详细的
         分析过程日志和最终综合评分。

  Step 4 — 可视化展示（可选）：启动 web_server.py，在浏览器中上传
         数据文件，查看包含健康评分仪表盘、三维雷达图和各维度信号
         分析图表的交互式界面。

  Step 5 — 运维决策：根据综合评分和历史趋势，运维系统自动生成调度
         指令——正常服役 / 重点观察 / 回收维修。

2.2.3  松耦合设计的工程收益

三层架构为本项目带来了显著的实际收益：

  (a) 采集端可替换为ESP32嵌入式方案：只需将ESP32的传感器数据按
      相同CSV格式写入SD卡，算法端无需任何修改即可分析。

  (b) 算法端可独立测试：开发者可在任意平台上用测试数据集验证算法
      正确性，无需连接安卓设备。

  (c) 可视化端可独立升级：前端UI框架可以从Flask+ECharts迁移为
      更现代的React+D3.js或Vue+Plotly，后端JSON API无需调整。

  (d) 并行开发：三人团队中一人负责Android采集、一人负责Python
      算法、一人负责Web界面——三者只需约定文件格式即可并行推进。



2.3  硬件平台分析
================================================================

2.3.1  为什么选择安卓手机而非专用嵌入式硬件

本项目在设计初期评估过两种硬件方案：

  方案A（专用嵌入式）：ESP32-S3 + MPU6050 IMU + MEMS麦克风模块 +
  GPS/北斗模块 + 霍尔传感器 + 锂电池。优点是可深度定制采样参数、
  传感器布局经过机械优化（如IMU紧贴花鼓可获得信噪比更高的振动信号）。
  缺点是硬件成本约¥200~300/套、需要结构设计（外壳+夹具）、量产和
  维护需要供应链管理。

  方案B（手机方案）：使用巡检人员自带的安卓手机。优点是硬件成本为
  零（手机已有），无需任何结构设计或供应链管理，部署门槛极低。缺点
  是传感器精度受限于手机型号、采样位置不固定（手机放口袋vs支架vs
  手持）、无法安装霍尔传感器直接测车轮转速。

综合评估后，本项目选择方案B（手机方案）。决定性因素并非成本（¥200
在百万辆车队面前也不容忽视），而是方案A的结构设计复杂性——将传感器
模块可靠地固定在共享单车上且每次骑行前后都需拆装，在实际运维场景中
的操作可行性存疑。相比之下，手机方案只需巡检人员将手机放入口袋或
手机支架即可完成操作，学习成本为零。

方案A作为未来硬件迭代方向写入第十三章的展望部分。

2.3.2  安卓手机传感器能力分析

以2024年主流的中端安卓手机（骁龙7系/天玑8000系平台）为基准，其
传感器子系统通常包含以下与本项目相关的组件：

  (1) 六轴IMU（加速度计+陀螺仪）
      型号通例：InvenSense ICM-4x 系列或 Bosch BMI 系列
      加速度计：±16g量程，16-bit分辨率，输出数据率最高800Hz
      陀螺仪：±2000°/s量程，16-bit分辨率，输出数据率最高800Hz
      噪声密度：加速度计约150 μg/√Hz，陀螺仪约0.005°/s/√Hz

      本项目实际使用：加速度计100Hz（SENSOR_DELAY_GAME），陀螺仪
      50Hz（SENSOR_DELAY_GAME/2）。选择此采样率而非最高的800Hz的
      原因：(a) 车轮振动信息集中在40Hz以下，100Hz足以满足奈奎斯特
      要求；(b) 过高采样率导致文件体积和功耗无谓增加；(c) Android
      传感器框架的SENSOR_DELAY_FASTEST模式在不同设备上行为不一致，
      实际有效采样率波动远大于名义值，SENSOR_DELAY_GAME的100Hz是
      跨设备兼容性最好的选项。

  (2) GNSS定位芯片
      支持GPS L1 + 北斗B1I双频
      定位更新率：最高10Hz（通过LocationManager.requestLocationUpdates
      指定100ms最小间隔）
      速度精度：约0.1 m/s（静态），0.3 m/s（动态>5km/h）
      航向精度：约2~5°（正常速度直行状态，由连续定位点推算）

      本项目实际使用：GPS_PROVIDER 10Hz为主力 + NETWORK_PROVIDER 5s
      为备用（GPS信号丢失时通过基站/WiFi辅助定位保持可用）。

  (3) MEMS麦克风
      Android AudioRecord 能力：
        采样率：8000 / 11025 / 16000 / 22050 / 44100 / 48000 Hz
        编码：ENCODING_PCM_16BIT
        声道：CHANNEL_IN_MONO
      本项目选用 8kHz 单声道 PCM，理由同2.1.2节(C2)。

2.3.3  手机传感器在自行车检测场景下的信噪比评估

将手机MEMS传感器用于机械故障检测，最关键的问题是：在手机的安装方式
（口袋/支架/手持）下，信号中是否包含足够的故障信息？

本文在此做一个粗略的可行性评估：

  加速度计噪声基底：150 μg/√Hz × √100Hz ≈ 0.0015 m/s² RMS
  车轮偏摆产生的典型振动幅值（经验估计）：0.05~0.5 m/s²
  信噪比 ≈ 20×log₁₀(0.05/0.0015) ≈ 30 dB —— 足够。

  陀螺仪噪声基底：0.005°/s/√Hz × √50Hz ≈ 0.035°/s RMS
  车头不正导致的偏航角速率偏置（经验估计）：0.3~3.0°/s (2秒观测窗口)
  信噪比 ≈ 20×log₁₀(0.3/0.035) ≈ 18 dB —— 边界可用，需多窗口平均。

  麦克风：8kHz/16-bit，理论动态范围96dB。
  链条异响声压级约60~75 dB SPL (@10cm)
  环境背景噪声约40~55 dB SPL（安静街道）或60~75 dB SPL（繁忙道路）
  在最差情况下信噪比接近0dB，这正是F2需要包络谱+Cepstrum双通道检测
  而不是简单能量判断的原因。

结论：手机传感器对F1信噪比充裕，F3边界可用需累积窗口，F2在嘈杂环境
信噪比紧张需依靠周期性特征区分噪音。这也解释了为何F2的算法设计最为
复杂——它是对信噪比不足的补偿。

2.5  核心设计决策与权衡
================================================================

本节记录四个贯穿整个项目的关键设计决策及其背后的权衡分析。

2.5.1  决策一：离线分析优于实时检测

项目最初的需求文档中提到"边采集边分析"，但我们在实施阶段选择了
离线分析路线（采集完成后运行Python脚本）。原因如下：

  优势：
    - 算法迭代独立于App发布周期。修改F2的特征权重无需重新编译APK
      和上架应用商店。
    - 可以使用Python的科学计算生态（NumPy/SciPy），无需在Android端
      实现FFT/滤波等底层算法。
    - 可以进行全局性的数据预处理（如自适应窗口选取），这需要完整
      时间序列的信息，实时流式处理难以实现。

  代价：
    - 巡检工作流多一个"导出数据→运行脚本"的步骤。
    - 无法在骑行过程中即时反馈健康状态。

  未来方向：端侧部署（见第十三章展望）。将核心算法移植为
  TensorFlow Lite或ONNX模型，在Android端实现近实时分析。

2.5.2  决策二：零机器学习优于监督学习

F2链条异响检测是系统中最难的问题——区分周期性金属冲击与随机环境
噪音。一个直观的思路是采集大量标注音频，训练一个CNN或SVM分类器。
本文最终选择了纯信号处理方案（包络谱+Cepstrum），理由如下：

  优势：
    - 零标注成本。不需要请自行车技师逐车诊断并录制"异响/无异响"
      音频数据集。
    - 可解释性强。包络谱SNR、谐波比例、相位一致性——每个特征都有
      明确的物理含义，运维人员可以理解。
    - 泛化能力好。物理规律（周期性冲击在包络谱中产生峰值）不会因
      城市、车型、天气变化而改变。而机器学习模型在这些分布外数据
      上的表现难以保证。

  代价：
    - 特征工程复杂度高。需要深入理解希尔伯特变换、倒谱、圆形方差
      等信号处理概念。
    - 可能在某些极端工况下不如训练充分的大模型准确。

  事实证明，纯信号处理方案在五组测试数据上已能给出合理的评分区分
  （参见第十二章），在缺乏大规模标注数据的情况下是完全可行的。

2.5.3  决策三：GPS松耦合优于强制依赖

GPS信号在城市环境中不稳定，如果F1和F3强制依赖GPS，则系统在隧道/高架
等场景下将完全失效。我们采用"松耦合"策略：

  - 有GPS：利用速度计算轮频先验（F1缩小FFT搜索范围），利用航向角
    作为直行段的ground truth（F3 GPS模式）。
  - 无GPS：F1全范围扫描轮频（1.5~8Hz），F3降级为IMU自估计模式。

  优势：系统在任何环境下都能给出结果，只是精度有所差异。
  代价：F3降级模式的精度明显低于GPS模式（见12.4节实验分析）。

2.5.4  决策四：CSV文本格式优于二进制格式

传感器数据选择了CSV纯文本存储而非Protocol Buffers、HDF5等二进制格式。

  优势：
    - 人类可读：用任何文本编辑器或Excel即可打开查看，方便调试和
      手动检查。
    - 跨语言通用：Python/Java/C++/MATLAB无需任何库即可解析。
    - 容错性好：局部数据损坏不影响其余行的读取。

  代价：
    - 文件体积约为二进制格式的2~5倍。
    - 浮点数格式化写入有精度损失（但"%.4f"在传感器精度范围内充足）。

  考虑到典型数据量（一次骑行<200MB）在现代存储介质上完全可接受，
  CSV的工程便利性远胜于二进制格式的微小体积优势。



2.6  系统安全与隐私设计
================================================================

本系统涉及GPS定位和音频录制两类敏感数据，安全与隐私保护不可忽视。

2.6.1  权限最小化原则

App仅申请完成数据采集功能所必需的权限：
  - ACCESS_FINE_LOCATION：GPS精确位置（采集端核心功能）
  - RECORD_AUDIO：麦克风录音（采集端核心功能）
  - FOREGROUND_SERVICE + 各类型权限：前台服务保活（系统要求）
  - WAKE_LOCK：CPU休眠控制（防止长时间采集中断）

不申请网络权限（不连接任何服务器）、不申请读取联系人/短信/相册等与
功能无关的权限。

2.6.2  数据本地化

所有采集数据100%保存在手机本地存储，App不包含任何网络传输代码。
数据从手机到PC的传输完全由巡检人员手动操作（USB复制或本地云盘），
不存在自动上传行为。这一设计从根本上消除了数据泄露的网络攻击面。

2.6.3  数据最小化

采集的GPS轨迹和音频数据仅用于算法分析，分析完成后巡检人员可自行
删除。算法层不保存原始数据副本——输入文件被读取后不进行任何复制
或缓存。

2.8  本章小结
================================================================

本章建立了系统的整体框架。核心要点如下：

  (1) 三层架构（采集→算法→可视化）以标准化文件格式为界，实现了
      各层独立开发、独立替换、独立演进的松耦合体系。

  (2) 安卓手机作为采集硬件具备充足的传感器信噪比（F1约30dB，F3约
      18dB，F2边界可用），在接近零成本的前提下满足检测需求。

  (3) 四个关键设计决策——离线分析优于实时检测、零ML优于监督学习、
      GPS松耦合优于强制依赖、CSV文本优于二进制——贯穿整个项目，
      每项都经过了明确的权衡分析。

  (4) 安全设计遵循权限最小化、数据本地化、数据最小化三原则，从
      架构上消除隐私泄露风险。

从第三章开始，本文将自底向上逐层展开详细设计：先讲Android采集端
（第三章和第四章），再讲数据预处理（第五章），最后讲算法核心
（第六至第九章）。
