================================================================
    共享单车多传感器数据采集与健康检测系统

    第五章  数据格式与预处理
================================================================

本章处于系统架构的"枢纽"位置——向上承接Android采集端输出的原始
文件，向下为三级故障检测管线准备清洁且对齐的数据。在此之前还需要
阐明一个重要问题：当一次骑行采集长达数分钟甚至十几分钟时，并非
所有数据都适合直接送入分析管线。我们需要一个智能的预处理策略。


5.1  传感器数据文件格式（传感器数据.txt）
================================================================

5.1.1  文件结构总览

Android采集端输出的合并传感器文件是一个纯文本CSV，由表头行和
数据行两部分组成。以一次约5分钟的骑行采集为例，文件大致如下：

  timestamp_ns,传感器类型,ax(m/s²),ay(m/s²),az(m/s²),纬度,经度,速度(m/s),航向角(°),gx(rad/s),gy(rad/s),gz(rad/s)
  4840231932000,加速度计,-0.0524,0.1478,9.7465,,,,,,,
  4840232148000,陀螺仪,,,,,,,,0.0012,-0.0007,0.0054
  4840232155000,加速度计,-0.0471,0.1521,9.7532,,,,,,,
  ...（数万至数十万行）
  4840500000000,加速度计,-0.0372,0.1047,9.7158,,,,,,,

  共计12个字段（逗号分隔），含义如下：

  ┌─────────────┬──────────┬──────────────────────────────────┐
  │ 列序号       │ 字段名    │ 说明                              │
  ├─────────────┼──────────┼──────────────────────────────────┤
  │ 1           │ timestamp_ns│ 纳秒时间戳（系统单调时钟）         │
  │ 2           │ 传感器类型  │ "加速度计" / "陀螺仪" / "GPS"      │
  │ 3–5         │ ax,ay,az  │ 三轴加速度 (m/s²)，仅加速度计行有值  │
  │ 6–7         │ 纬度,经度  │ WGS84坐标 (°)，仅GPS行有值          │
  │ 8           │ 速度      │ 地面速率 (m/s)，仅GPS行有值          │
  │ 9           │ 航向角     │ 地面航向 (°)，仅GPS行有值            │
  │ 10–12       │ gx,gy,gz  │ 三轴角速度 (rad/s)，仅陀螺仪行有值   │
  └─────────────┴──────────┴──────────────────────────────────┘

5.1.2  稀疏列填充策略

CSV文件的每一行仅填充对应当前传感器类型的字段，其余字段留空
（两个逗号之间无内容）。例如：

  加速度计行：时刻,加速度计,0.05,-0.11,9.81,,,,,,,
  陀螺仪行：  时刻,陀螺仪,,,,,,,,0.01,0.00,0.05
  GPS行：     时刻,GPS,,,,39.900,116.380,5.42,87.3,,,

这种"稀疏列"设计的初衷是将三种传感器的数据统一到一个易于浏览的
文件中（用Excel打开即可直观对比各传感器的时间顺序），代价是文件
中存在大量空白字符。相比每种传感器独立一个文件，合并文件的方案在
工程调试阶段的便利性是决定性优势——开发者只需在一个终端窗口中
`tail -f` 即可同时观察所有传感器的输出节奏。

5.1.3  格式的版本兼容性

文件格式经历了两次演化：

  v2格式（无GPS）：
    加速度计行：timestamp_ns,加速度计,ax,ay,az,,,,,,gx,gy,gz
    陀螺仪行：  timestamp_ns,陀螺仪,,,,,,,,gx,gy,gz
    特点：加速度计行同时填充了加速度和陀螺仪数据（第10-12列），
    陀螺仪行与加速度计行形成冗余。

  v4格式（有GPS）：
    加速度计行：timestamp_ns,加速度计,ax,ay,az,,,,,,,
    陀螺仪行：  timestamp_ns,陀螺仪,,,,,,,,gx,gy,gz
    GPS行：     timestamp_ns,GPS,,,lat,lon,speed,course,,,
    特点：三路传感器各行独立，不再在加速度计行中填充陀螺仪值。

Python算法端的 load_sensor_data() 函数支持两种格式的自动检测。
检测逻辑是：遍历前若干行，若存在"GPS"类型标签或速度字段非空
的行，则以v4模式解析；否则以v2模式解析。这种"嗅探式"兼容策略
使得来自不同版本App的历史采集数据都可以被统一处理。

5.1.4  数据加载实现

load_sensor_data() 的核心逻辑如下（伪码）：

  def load_sensor_data(path):
      accel, gyro, gps = [], [], []

      for line in lines[1:]:
          parts = line.split(",")
          ts = int(parts[0])
          stype = parts[1].strip()

          if stype == "加速度计":
              accel.append(AccelSample(ts, float(az)))
          elif stype == "陀螺仪":
              gyro.append(GyroSample(ts, float(gz)))
          elif stype == "GPS":
              speed  = float(parts[7]) if parts[7] else 0.0
              course = float(parts[8]) if parts[8] else 0.0
              gps.append(GpsSample(ts, lat, lon, speed, course))

      return accel, gyro, gps

  三个关键防御点：
    ① 空字符串保护：GPS的速度/航向字段可能为空（对应信号中断场景），
       在 float() 转换前先检查字符串是否为空。
    ② 列数不足保护：若某行逗号数量不足12个，跳过该行（数据损坏
       或写入过程中App崩溃的残留行）。
    ③ 类型标签精确匹配：使用 strip() 消除Android端写入时可能引入
       的尾部空格。



5.2  音频数据格式
================================================================

5.2.1  PCM原始音频

音频文件（音频.pcm）采用最小化的存储格式——无文件头、无压缩、
无编码容器的裸PCM数据：

  · 编码：16-bit 有符号整数，小端字节序
  · 采样率：8000 Hz（标称值）
  · 声道数：1（单声道）
  · 文件大小(字节) = 采样点数 × 2

  选择裸PCM而非WAV/WEBM/OGG等容器格式的理由是避免依赖任何音频
  解码库。Python端只需 struct.unpack("<Nh", raw_bytes) 即可解析，
  无需引入libav/ffmpeg/pydub等第三方包。

  load_audio() 的实现极为简洁：

    raw = open(path, "rb").read()
    n = len(raw) // 2
    samples = array("h")  # 有符号16位
    samples.frombytes(raw)
    return samples.astype(float32) / 32768.0  # 归一化到[-1, 1]

5.2.2  音频时间戳元数据

音频_时间戳.csv 是音频数据的时间索引。其格式为：

  timestamp_ns,累计采样数
  4840234000000,0
  4840235210000,2048
  4840236420000,4096
  ...

  首行为表头，后续每行记录一次 AudioRecord.read() 完成后的状态。

  "累计采样数"的含义是"从录制开始到此刻总共采集的采样点数"，
  而非"本次read返回的采样点数"。这是一个累加值（monotonic
  counter），因此即使在写入过程中某一行丢失，下一行的累计值
  仍然正确，不会累积误差。

  在算法端，若需要在时间 T 附近定位音频数据，则：
    ① 在CSV中找到最接近T的两个时间戳行
    ② 线性插值计算T对应的累计采样数
    ③ 在PCM数组中定位到 累计采样数 × 2 的字节偏移量

  元数据的写入频率等于AudioRecord.read()的返回频率。在8kHz、
  minBufSize≈800字节的条件下，每次读取约80ms的音频数据（约640
  个采样点），15分钟产生约11,000行元数据。这个密度足以支撑
  毫秒级的音频定位精度。

5.2.3  实际采样率估算

虽然AudioRecord被配置为8kHz，但实际采样率受晶体振荡器公差影响
存在微小偏差（约±20 ppm，即±0.16 Hz）。在长时间采集中，这个
偏差会导致理想时间与累计采样数之间产生可观的漂移。例如：

  实际采样率 = 8000.1 Hz（+12.5 ppm偏差，完全在晶体公差内）
  15分钟后：
    理想采样数 = 8000 × 900 = 7,200,000
    实际采样数 = 8000.1 × 900 = 7,200,090
    偏差 = 90采样点 ≈ 11毫秒

  对于FFT和包络谱分析而言，11ms的偏差完全可忽略。但对于需要
  精确时间对齐的应用（如音视频同步），这个偏差是需要修正的。
  本项目通过元数据CSV中的{timestamp → cumulative_samples}映射
  自然纠正了这一偏差——无论实际采样率是多少，时间到采样索引的
  映射始终准确。

  在无元数据的情况下（例如旧版采集数据），采样率通过首尾两个
  AudioChunk的时间差和采样数差估算：

    estimated_fs = Δsamples / Δtime

  并限制在 [1000, 96000] 的合理范围内作为防御。



5.3  大数据自适应窗口选取算法
================================================================

这是数据预处理阶段的核心创新。本节将详细阐述问题背景、算法设计和
实现细节。

5.3.1  问题背景

一次典型的巡检骑行持续5~15分钟。以15分钟为例：
  · 加速度计：100Hz × 900s = 90,000条
  · 陀螺仪：50Hz × 900s = 45,000条
  · 音频：8000Hz × 900s = 7,200,000采样点

  若将全部音频数据送入F2的包络谱分析（包含希尔伯特变换、滤波、
  FFT、Cepstrum等运算），处理时间可能超过2分钟——超出了2.1.2节
  设定的30秒实时性约束。

  更重要的是，并非所有时间段都适合故障分析。骑行过程中包含：
    · 起步加速段：速度不稳定，GPS数据波动大
    · 转弯段：陀螺仪Z轴偏航角速度大，F3无法使用
    · 颠簸路段：加速度计高方差，F1平整路面判定失效
    · 减速刹车段：各种信号都有瞬态大扰动
    · 平稳直行段：所有检测器的最佳工作条件 ✓

  由此产生一个自然的问题：能否自动从长数据中定位出最适合分析的
  短时间段？

5.3.2  算法设计思路

  输入：
    accel : list[AccelSample]（全部加速度计数据）
    gyro  : list[GyroSample]（全部陀螺仪数据）
    audio : np.ndarray（全部音频数据）
    audio_ts : list[AudioChunk]（全部音频时间戳）
    gps   : list[GpsSample] | None（GPS数据，可选）

  参数：
    MAX_DURATION_S    = 30s  — 触发窗口选取的阈值
    WINDOW_DURATION_S = 15s  — 选取的窗口长度
    （以上两个参数可通过环境变量 BIKE_MAX_DURATION_S 和
     BIKE_WINDOW_DURATION_S 覆盖）

  输出：
    一个字典，包含 used_window 标志位和裁剪后的切片数据。
    若未触发窗口选取（数据短于30s），返回原始数据引用。

  触发条件：
    (传感器时长 > 30s) OR (音频时长 > 30s)
    两者满足其一即触发。这样设计的理由是：传感器数据和音频数据
    的时长可能因采集启动/停止时序的微小差异而不完全相同。

5.3.3  窗口评分函数

  核心问题：如何量化"这个时间窗口适合做故障分析"？

  我们定义了三维评分指标，每个维度都是"越低越好"：

    维度一：路面平整度
      score₁ = variance(az_filtered[window])
      · 物理意义：加速度计Z轴的方差反映路面颠簸程度。
      · 偏向选择方差低（路面平整）的窗口，此时F1的FFT更干净，
        轮频峰值更突出。

    维度二：直行稳定性
      score₂ = variance(gz[window]) × 10
      · 物理意义：陀螺仪Z轴的方差反映转弯幅度。
      · 乘以10的权重系数，使直行稳定性成为窗口选择中的主导因素。
        因为：a) 转弯时F3完全无法工作（GPS航向剧烈变化），
        b) 转弯时的离心力对加速度计产生额外低频干扰。
      · 偏向选择方差低（几乎不转弯）的窗口。

    维度三：匀速偏好
      score₃ = variance(gps_speed[window]) × 5 (归一化后)
      · 物理意义：GPS速度的方差反映速度是否稳定。
      · 偏向选择方差低（匀速骑行）的窗口。因为匀速段的车轮转频
        恒定，FFT频谱中的轮频峰更尖锐集中。
      · 权重5.0介于平整度(1.0)和直行(10.0)之间。
      · 仅在GPS数据可用且时间范围与加速度计有重叠时才计算；
        无GPS时此维度为0（不参与评分）。

  综合评分向量（向量化计算）：
    scores = az_var × 1.0 + gz_var × 10.0 + gps_speed_var × 5.0

  取 argmin 即为最优窗口。

5.3.4  向量化实现

  窗口扫描的朴素实现需要 O(N × W) 的时间复杂度（N个候选起点，
  每个起点计算W长度窗口的方差）。借助NumPy的 sliding_window_view，
  可以在 O(N) 时间内完成所有候选窗口的方差计算——一次向量化
  操作直接得到所有窗口的方差数组。

  实现步骤：

    Step 1 — 统一重采样到50Hz
            将加速度计和陀螺仪的非均匀时间序列重采样到50Hz均匀
            网格。目标采样率不需要很高——窗口评分关注的是一秒
            以上时间尺度的统计特性，50Hz足够。

    Step 2 — 构建滑动窗口（向量化单行代码）
            from numpy.lib.stride_tricks import sliding_window_view

            window_len = int(WINDOW_DURATION_S * 50)  # 15s × 50 = 750样本
            step = window_len // 4                       # 步长为窗口的1/4

            az_windows = sliding_window_view(az, window_len)[::step]
            az_vars = az_windows.var(axis=1)  # 所有窗口的方差，一次性计算

            gz_windows = sliding_window_view(gz, window_len)[::step]
            gz_vars = gz_windows.var(axis=1)

            # 同理处理GPS速度（插值到统一时间轴后）
            speed_vars = ...

    Step 3 — 综合评分 + argmin
            scores = az_vars + gz_vars * 10.0 + speed_vars * 5.0
            best_idx = argmin(scores)

    Step 4 — 计算最佳窗口的起止时间
            best_start_ns = t_min_ns + best_idx * step / 50 * 1e9
            best_end_ns   = best_start_ns + WINDOW_DURATION_S * 1e9

5.3.5  数据裁剪

  确定了最佳窗口的起止时间戳后，需要对三类数据进行裁剪：

  —— 传感器数据裁剪（按时间戳过滤）——

    accel_slice = [a for a in accel
                   if best_start_ns <= a.timestamp_ns < best_end_ns]
    gyro_slice  = [g for g in gyro
                   if best_start_ns <= g.timestamp_ns < best_end_ns]

   时间复杂度O(N)，对90,000条记录约需数毫秒。

  —— 音频数据裁剪（按累计采样索引定位）——

  音频裁剪比传感器复杂——需要通过元数据CSV将"时间戳"转换为
  "PCM数组中的偏移量"。

    Step 1：在音频元数据中找到最接近窗口起止时间的行索引。

    Step 2：获取对应的累计采样数：
            sample_start = audio_ts[start_idx].cumulative_samples
            sample_end   = audio_ts[end_idx].cumulative_samples

    Step 3：切片PCM数组：
            audio_slice = audio[sample_start : sample_end]

    Step 4：调整元数据CSV中的累计采样数（重新对齐到窗口起点）：
            for chunk in audio_ts_slice:
                chunk.cumulative_samples -= sample_start

      这一步是关键的——裁剪后的音频数据的累计采样数必须从接近零
      的值开始，否则后续的采样率估算和时间定位会出现系统性偏差。

  —— GPS数据裁剪 ——

  GPS数据在窗口选取函数之外进行裁剪（见main函数），使用相同的
  时间戳过滤方式：

    gps_slice = [g for g in gps
                 if best_start_ns <= g.timestamp_ns < best_end_ns]

  裁剪后的GPS数据用于F1的轮频先验和F3的航向对比。

5.3.6  算法局限性与适用条件

  自适应窗口选取算法在以下条件下效果最佳：

    ✓ 数据中存在至少一段平稳直行（大多数常规骑行满足）
    ✓ 传感器时长 > 30秒（短于此时不触发，直接全量分析）
    ✓ GPS数据可用（无GPS时速度维度退化为0，仅靠az+gz评分）

  在以下条件下效果可能不理想：

    ✗ 全程都在小巷中反复转弯（没有一个窗口的gz方差低）
    ✗ 全程严重颠簸（没有一个窗口的az方差低）
    ✗ 数据极短（< 30秒不触发选取，无所谓好坏）

  需要强调的是：窗口选取算法只是"从长的数据中选一个最好的窗口"，
  而非"判断数据是否足够好"。如果全程都是较差条件，选出的窗口
  确实是最优的，但各检测器的置信度会普遍偏低（平整路面占比低、
  直行段短），最终综合评分会通过置信度加权机制体现这种不确定性。

5.3.7  环境变量配置

  窗口选取算法的两个关键参数均支持环境变量覆盖：

    export BIKE_MAX_DURATION_S=20    # 更激进的全量分析阈值
    export BIKE_WINDOW_DURATION_S=10 # 更短的窗口

  这一设计允许在不修改代码的情况下适配不同的使用场景。例如：
    · 快速筛查模式：WINDOW_DURATION_S=8，缩短处理时间
    · 精细分析模式：WINDOW_DURATION_S=20，使用更长的分析窗口
    · 强制全量模式：MAX_DURATION_S=999999，永远不触发窗口选取

  运行时读取方式：
    MAX_DURATION_S = float(os.environ.get("BIKE_MAX_DURATION_S", "30"))


5.4  本章小结
================================================================

本章建立了连接采集端与算法端的数据桥梁。核心要点：

  (1) CSV合并文件的稀疏列填充策略以少量存储冗余换取了跨传感器
      时间对比的直观性。格式的v2/v4版本自动兼容消除了历史数据
      的迁移压力。

  (2) 音频采用裸PCM+元数据CSV的双文件方案，以最小的解码依赖
      实现了精确的时间→采样索引映射。

  (3) 自适应窗口选取算法是本章的核心创新——通过三维评分向量
      （路面平整度+直行稳定性+匀速偏好）的向量化计算，在O(N)
      时间内自动定位最优分析窗口，将长时间数据压缩为15秒高质量
      片段，为后续三级检测管线提供理想的输入信号。

  (4) 所有预处理函数均包含防御性编程——空数组保护、采样率限幅、
      窗口长度不足时退回全量模式——确保在数据质量不佳时优雅降级。
