================================================================
    共享单车多传感器数据采集与健康检测系统

    第十章  Web 可视化仪表盘
================================================================



10.1  设计目标
================================================================

Web 可视化仪表盘是系统的用户交互层，承担三个核心职能：

  (1) 数据上传入口：巡检人员在 PC 端通过浏览器上传 Android 采集端
      输出的三个文件，触发后台检测。

  (2) 结果可视化：将算法输出的多维检测数据转化为直观的图表——
      健康评分仪表盘、三子项雷达图、各维度的信号波形和频谱图。

  (3) 独立可运行：不依赖用户认证系统或数据库即可使用（本地文件
      模式），同时也支持完整的骑行记录+用户认证生产模式。



10.2  系统架构
================================================================

仪表盘采用前后端分离的单页应用架构：

  ┌──────────────────────────────────────────────────┐
  │  浏览器（单页 HTML）                                │
  │  · 文件拖拽上传区（3 个 file input）                │
  │  · ECharts 仪表盘 + 雷达图 + 波形/频谱              │
  │  · 实时状态反馈（上传中 → 分析中 → 结果展示）        │
  │  · Fetch API + FormData 异步提交                   │
  └──────────────────────┬───────────────────────────┘
                         │ POST /api/detection/process
                         │ (multipart/form-data)
  ┌──────────────────────▼───────────────────────────┐
  │  FastAPI 后端（Python）                             │
  │  · 接收三个文件（传感器 CSV + PCM + 时间戳 CSV）     │
  │  · 调用 detection_engine → 三级检测管线             │
  │  · 构建图表数据（波形采样、FFT 频率/幅值对）         │
  │  · 返回 JSON（健康评分 + 图表数据 + 数据摘要）       │
  └──────────────────────┬───────────────────────────┘
                         │
  ┌──────────────────────▼───────────────────────────┐
  │  算法层（bike_health_detector.py）                 │
  │  · parse_sensor_csv / parse_pcm / parse_audio_ts  │
  │  · select_analysis_window                         │
  │  · run_full_detection                             │
  └──────────────────────────────────────────────────┘

10.3.1  前端设计

10.3.1  视觉主题

仪表盘采用深色科技风配色方案，专为巡检现场的使用场景设计：

  · 背景：深蓝黑 (#0f1923) —— 减少视觉疲劳，户外环境在笔记本屏幕
    上也保持足够的对比度。
  · 卡片：蓝灰 (#1a2736) + 微弱边框 —— 清晰的区块分隔，信息层级
    一目了然。
  · 功能色：
    - 绿色 (#00e676) → 评分 ≥75 / 推荐骑行
    - 黄色 (#ffab00) → 评分 50~74 / 谨慎使用
    - 红色 (#ff1744) → 评分 <50 / 建议换车
    - 蓝色 (#448aff) → 交互元素（按钮、高亮）
    - 紫色 (#7c4dff) → F3 专属色
    - 青色 (#18ffff) → F2 专属色

  配色设计的核心原则：**不看文字也能感知状态**。巡检人员只需一瞥
  评分数字的颜色（绿/黄/红）即可做出调度决策，无需阅读任何文字
  说明。

10.3.2  页面布局

仪表盘页面自上而下分为三个功能区：

  (A) 文件上传区

      三个可点击的文件选择框，分别对应传感器数据.txt（📊图标）、
      音频.pcm（🎵图标）、音频_时间戳.csv（⏱️图标）。

      每个选择框在文件被选中后变为绿色边框 + "已选择"标签，提供
      即时的操作反馈。三个文件全部选择后「开始检测」按钮解锁。

      额外提供「📂 使用测试数据」按钮，一键加载 data/ 目录中预置的
      示例文件，方便演示和功能验证。

  (B) 综合评分区（左侧栏）

      · ECharts 仪表盘图表：半圆形速度表，指针指向当前评分，颜色
        随评分等级自动变化（绿/黄/红）。
      · 大号评分数字（42px 字体）—— 页面中最显眼的元素。
      · 推荐横幅：绿色"推荐骑行" / 黄色"谨慎使用" / 红色"建议换车"，
        带对应半透明背景色。
      · 三子项评分卡片：F1/F2/F3 各自的大号数字 + 进度条 + 关键指标
        （P 值/SNR/Δθ）。

  (C) 详细分析区（右侧主区域）

      · F1 详情卡片：Z 轴加速度原始波形 + FFT 频谱图（双列布局）。
      · F2 详情卡片：音频波形（前 1 万采样点）+ FFT 频谱（前 8192
        采样点的短时频谱）。
      · F3 详情卡片：三轴陀螺仪波形 + 累计偏航角曲线。
      · 数据摘要卡片：加速度计数 / 陀螺仪数 / 音频采样数 / 窗口信息。

10.3.3  交互流程

  用户操作路径：
    ① 选择/拖拽三个文件 → 文件框变绿
    ② 点击「开始检测」→ 按钮禁用 + 加载动画（旋转圆环 + "正在分析
       传感器数据与音频特征..." 提示）
    ③ 等待（通常 5~15 秒）→ 上传区隐藏，结果区展示
    ④ 浏览各维度结果 → 如需重测，刷新页面重新上传

  异步提交使用 Fetch API + FormData：

    const fd = new FormData();
    fd.append('sensor', fileSensor);
    fd.append('audio_pcm', filePcm);
    fd.append('audio_ts', fileTs);
    const r = await fetch('/api/detection/process', {method:'POST', body:fd});
    const result = await r.json();

  注：当前版本的加载提示中展示了"FFT 频谱分析 · MFCC 特征提取 ·
  SVM 推理"的技术名词——这是在算法 v2.0 阶段的遗存。v3.0 已将 MFCC+
  SVM 替换为包络谱+Cepstrum 方案，前端文案可通过修改 HTML 模板中的
  loading 区域文字进行同步更新。



10.4  API 设计
================================================================

10.4.1  独立文件上传接口（无需认证）

    POST /api/detection/process
    Content-Type: multipart/form-data

    参数：
      sensor     — 传感器数据.txt（CSV 文本，UTF-8）
      audio_pcm  — 音频.pcm（16-bit LE PCM 二进制）
      audio_ts   — 音频_时间戳.csv（CSV 文本，UTF-8）

    返回 JSON：
      {
        "health": {
          "total_score": 72.2,
          "harmonic_mean": 84.4,
          "penalty_factor": 0.855,
          "level": "caution",
          "recommendation": "谨慎使用",
          "sub_scores": {
            "tire_wobble": 80.0,
            "chain_noise": 94.8,
            "handlebar_misalignment": 81.5
          }
        },
        "f1_charts": {
          "waveform": {"times": [...], "az_filtered": [...]},
          "fft": {"freqs": [...], "magnitude": [...]}
        },
        "f2_charts": { ... },
        "f3_charts": { ... },
        "data_summary": {
          "accel_count": 1498,
          "gyro_count": 749,
          "audio_samples": 120640,
          "audio_ts_blocks": 482
        }
      }

  该接口是旧版 Flask 实现的直接替换，无认证要求，适合巡检人员
  在本地笔记本上临时启动服务即可使用。

10.4.2  骑行关联的上传接口（需认证）

    POST /api/detection/upload/{ride_id}

  该接口与完整的骑行生命周期管理系统对接——先通过 /api/rides/start
  创建骑行记录，采集数据后上传至 /api/detection/upload/{ride_id}，
  检测结果自动关联到该骑行记录并存库。适用于部署到云端的生产环境。

10.4.3  在线仪表盘页面

    GET /api/detection/dashboard

  在无文件上传的情况下，自动读取 data/ 目录中的预置数据文件并渲染
  完整仪表盘。同时提供网页版文件上传功能，供交互式使用。

10.4.4  JSON 格式上传（Base64 编码）

    POST /api/detection/process-json

  为自动化流水线设计的接口，接受 JSON body 中 base64 编码的三个文件
  内容，无需使用 multipart/form-data。例如 CI 流程中可直接将文件
  内容序列化为 JSON 远程提交。



10.5  图表数据构建
================================================================

后端在完成检测计算后，额外构建三个维度的图表数据，供前端 ECharts
渲染。图表数据独立于检测结果（即使检测失败，图表仍可展示原始信号
以辅助人工分析）。

  F1 图表：
    · 波形图：Z 轴加速度的原始时域波形（time, az）。
    · 频谱图：Z 轴加速度的 FFT 幅值谱（freq, magnitude），从 0 Hz
      到 Nyquist 频率。该图直观展示了轮频处的峰值——对于偏摆车，
      轮频位置的幅值突出。

  F2 图表：
    · 波形图：音频前 10,000 采样点的时域波形（time, amplitude）。
      展示时间约 1.25 秒（@8kHz），足以覆盖数个踏频周期。
    · 频谱图：音频前 8,192 采样点的短时 FFT 频谱（freq, magnitude），
      频率覆盖 0~4kHz。链条异响表现为 2~4kHz 频带的高能量和踏频
      处的包络谱峰（后者需做 Hilbert 变换才能看到，此处仅展示原始
      FFT 供参考）。

  F3 图表：
    · 陀螺仪波形：三轴角速度（gx, gy, gz）时域波形。
    · 累计偏航角：gz 的累积积分（º），直观展示车把偏转的历史轨迹。
      健康车偏航角围绕零值波动，偏斜车则持续向一侧漂移。



10.6  本章小结
================================================================

  (1) Web 仪表盘作为系统的可视化出口，以深色科技风配色、ECharts
      交互图表和清晰的信息层级，为巡检人员提供即时的健康评估。

  (2) 前后端通过 multipart/form-data + JSON 的轻量接口解耦，前端
      纯静态 HTML（零构建工具依赖），后端 FastAPI 支持独立运行和
      生产部署两种模式。

  (3) 图表数据由算法层的辅助函数在检测过程中同步构建，无需前端
      进行任何信号处理运算。前端仅负责 ECharts 的 setOption() 调用。
